# 模型重载后的 GPU 资源增长

## 如何发现

浏览器检查连续重载同一个机械臂，并读取 Three.js 的 geometry 数量。初次测试出现 `7、64、83、102、121、140`，后几次每次增加约 19 个，说明同一模型反复加载后资源没有保持稳定。

## 原因

旧模型的 loader effect 在清理时调用了 geometry / material 的 dispose，但旧模型还可能留在场景中。React 的下一次提交与 Three.js 的渲染帧并不是同一件事。如果 WebGLRenderer 又画了一帧旧模型，已经 dispose 的 geometry 会被重新上传。

因此，“调用过 dispose”不能直接推导出“资源已正确释放”。还需要保证不再被绘制。

## 修复

在 loader 清理阶段，先 `owned.removeFromParent()` 把模型移出场景，再去重释放其独占的 geometry 和 material。这样即使下一次 React 提交稍晚，渲染器也不会继续画这个旧模型。

另一个边界是用于轨迹正向运动学采样的 clone。它共享原模型的 geometry，只计算变换，不进入渲染场景；不能从这个 clone 再释放共享的资源。

## 验证

修复后重新运行同样的六次重载，得到 `26、26、26、26、26、26`，浏览器没有页面错误。自动化检查位于 `scripts/browser-smoke.mjs`。

这些数字只说明本次模型重载场景下 geometry 数量稳定，不构成对全部 JavaScript 堆、GPU 内存和所有操作路径“没有泄漏”的证明。进一步验证需要对其他资源和使用场景做相应测量。
